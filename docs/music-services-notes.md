# Music services (SoundCloud, Spotify) notes

Branch `feature/music-services`, worktree `~/jf-music`, base `fix/3.2.2` @ 5796bc9. Design and rules:
`HANDOFF-music-channels.md` in the workspace root. Nothing here is released, pushed or deployed.

## Rules the code is held to

1. Stream only: no audio on disk, no offline mode, no cache of encrypted files.
2. No DRM circumvention. SoundCloud tracks whose only transcodings are `cbc-encrypted-hls` or
   `ctr-encrypted-hls` are hidden; their key URIs are never fetched. Snipped previews are skipped.
3. No other vendor's client credentials are used or extracted.
4. The client id, tokens and credential blobs are never logged or committed.

## SC0: network layer

* `source/net/sx_*` is a separate module; the Jellyfin path (`http.cpp`, firmware SSL) is untouched.
* `sx_tls_init()` runs in `main.cpp` right after `http_init()` / `net_selftest_run()` and before the VDEC
  reserve, because it allocates (RNG, parsed CA bundle) and the reservations leave little heap.
* Host: `make -f tests/Makefile.music check` (TLS/HTTP against a local server, ChaCha/AES, expired cert).
* Console check (the user's step): create `/dev_hdd0/tmp/jellyfin_sc_test.txt` (any content), start the app,
  then read `/dev_hdd0/tmp/jellyfin_sc_test_result.txt`. It walks the whole chain (client id, resolve, stream
  URL, playlist, init segment, segment 0) on a worker thread and deletes the gate file when it starts.

### Measured 2026-10-16 on this PC (host mbedTLS, same code)

* client id scrape 343-378 ms, resolve ~150-200 ms, stream URL ~60-95 ms, playlist ~220 ms, segment 0 ~80 ms.
* Bundled roots verify `soundcloud.com`, `api-v2.soundcloud.com`, the script host `a-v2.sndcdn.com` and the
  media CDN `playback.media-streaming.soundcloud.cloud` (Amazon chain).
* Signed media URLs are ~840 characters, so every URL buffer is `SC_URL_MAX` (1536).

## SC1: pure client (`source/svc/sc_*.c`)

* `sc_scan`: byte state machine for `client_id:"<32 alnum>"`. The same script holds `google_client_id:"..."`
  and `apple_id_client_id:"..."`; a hit needs a non-`[A-Za-z0-9_]` byte before it, exactly 32 alphanumerics and
  a closing quote. Tested with every split point and byte-at-a-time.
* `sc_hls`: media playlists. Any `EXT-X-KEY` / `EXT-X-SESSION-KEY` whose METHOD is not NONE is refused before a
  URI is looked at. Master playlists and byte ranges are refused. Durations are rounded to the millisecond.
* `sc_api`: URL builders, parsers and the transcoding rule (see header). `sc_url_with_cid` only ever adds the
  client id to `https://api-v2.soundcloud.com/`.
* `sc_net`: client id scrape, API calls with 401/403 refresh-and-retry, stream URL resolution. API URLs carry a
  placeholder; the real id is substituted for the one request on the stack.
* Fixtures: `tests/fixtures/sc/` (recorded 2026-10-16, secrets replaced). The real audio segments are
  all-rights-reserved and live only in the gitignored `tests/fixtures/sc-private/`.
* Test: `tests/svc/test_sc.c` (516 checks) x86 with ASan/UBSan and big-endian under `qemu-ppc64`.

## SC2: playback chain (source/svc/fmp4, sc_aac, sc_dec, sc_source)

`sc_source` (playlist + on-demand segment fetch, retry, signed-URL refresh) -> `fmp4` (init/segment reader) ->
`sc_aac` (libfaad, raw frames from the init segment's AudioSpecificConfig) -> `resample.c` -> 48 kHz stereo floats.
`sc_dec` has the shape of local_audio's `la_open` / `la_decode` / `la_seek`, so the music engine drives a SoundCloud
track the way it drives a file.

* The Yo! Player port's `demux-mp4.c` reads through a random-access video source, so `fmp4.c` is a rewrite for
  whole in-memory segments that follows its fragment handling (tfhd/trex defaults, tfdt, trun flags). No Yo! code is
  copied, so no Apache NOTICE is carried; the idea is credited in the header.
* Demux checked frame for frame against ffmpeg's demuxer on ffmpeg-made DASH segments (`fixtures/sc_synth/make.sh`,
  own tones, generated at test time): 1078 stereo and 564 mono frames identical, including truncation and byte-flip
  fuzzing. SoundCloud's real init segment parses (44.1 kHz, stereo, AAC-LC, 2-byte ASC).
* Decode checked against ffmpeg's decoder: max difference 1.4e-4 (mono 48 kHz) and 2.2e-4 (stereo 44.1 kHz through the
  resampler). **Big-endian: the same test under `qemu-ppc64` with libfaad 2.7 (the portlibs' version, built by
  `~/st-tools/faad-be/build.sh`) passes with max 1.44e-4 / 1.90e-4.** It takes about 3 minutes under qemu.
* Seeks: the segment's tfdt places the target exactly (the playlist's rounded EXTINF only picks the segment), two
  frames of lead-in are decoded and dropped. libfaad's PNS noise runs on across a stream, so a seek re-rolls noise in
  bands that use it: sample differences stay under 5e-4 against a 0.0625 tone.
* `scaac_reset` reopens the libfaad handle instead of `NeAACDecPostSeekReset`, so a seek to 0 is bit-identical to a start.

### Measured on this PC against the real service (`live_play`)

* Free track (Forss, "Flickermood"): playlist in 325 ms, first sound 423 ms after the playlist request, seeks produce
  audio in 38-118 ms, the last segment ends cleanly after 8.9 s, and a forced re-resolve (an expired URL) is
  transparent (`refreshes=1`).
* 23 real liked tracks from two profiles (160 and 96 kbit/s AAC, all 44.1 kHz): all decode, 0 bad frames.
* Not measured: console CPU and heap, TLS speed on the PS3, how long a segment takes there. That is the user's SC0/SC-TV step.

## Spotify: SP1 and SP2 done, SP0 not runnable here, and a premise of the handoff is wrong

**Status: stopped before any PS3 code (SP3/SP4) was written.** Reasons in order of weight:

### 1. cspot's playback chain uses Spotify's own web-player client id (handoff rule 1.3)

The handoff says cspot's Connect flow (zeroconf or a stored blob) is "the only auth". Reading the code says that is not
the whole flow. After the access-point login (which needs no client id), cspot asks for a bearer token from
`https://login5.spotify.com/v3/login` with a **hard-coded client id, `65b708073fc0480ea92a077233ca87bd`, commented in
the source as "Spotify web client's client id"** (`cspot/src/AccessKeyFetcher.cpp:31` in upstream, 2024-07;
Switify's modified cspot, 2026-08, moves it to `app/src/spotify_engine.cpp:63` and hands the token to cspot through
`accessTokenProvider`). That token is what the next step sends to
`https://api.spotify.com/v1/storage-resolve/files/audio/interactive/<file id>` (`TrackQueue.cpp:284`) to get the CDN
address of the audio, and for metadata. Without it there is no audio URL, so no playback;
cspot has no other route to the CDN address (its only `hm://` calls are metadata and the Connect remote channel).
librespot and go-librespot do the same.

That id is a public constant of Spotify's web player, not a secret and not a developer app, and it is the same kind of
thing as the SoundCloud web client id the SoundCloud tab scrapes (which the handoff plans on purpose). But rule 1.3 says
"Spotify's own client IDs taken from binaries", and this is Spotify's own id taken from a client. I did not decide
whether the rule's intent covers it; that is the user's call.

Other Spotify-defined values every Connect receiver sends (all in the AP handshake, none is a credential): the client
`BuildInfo` (product CLIENT, platform, version 112800721), a device id, and Spotify's published access-point public keys.

### 2. SP0 cannot run from WSL as it stands

SP0 needs the phone (or the PC's Spotify app) to discover a `_spotify-connect._tcp` device on the LAN. This WSL is in
NAT mode (`eth0` 172.23.28.12, no `.wslconfig`), so mDNS from WSL never reaches the LAN. Fixing that means changing the
networking mode and `wsl --shutdown`, which would stop every other session's WSL work, so it was not done.
Options for the pairing: (a) pair with the PS3 itself once the port exists (the PS3 answers mDNS on the LAN directly),
(b) switch WSL to mirrored networking at a moment the user chooses, (c) run `cspotcli -u <name> -p <password>
-c creds.json` in the user's own terminal (their password, typed by them; not zeroconf, so it needs the user's OK too).
The upstream cspot CLI built and linked on the host (`~/sp/build-host`, g++ 15, mbedTLS 3.6, NamedPipe sink); it was
not run against Spotify.

### 3. SP1: does cspot compile with GCC 7.2? Yes, with a small shim (no C++20, no mbedTLS 3)

`ppu-g++` 7.2, `-std=gnu++17`, mbedTLS 2.28 headers from the portlibs, over every cspot and bell source except the
platform layer and the MP3/Opus codecs (Spotify uses Vorbis): 54 files.

* C++20 features in code we need: `std::endian` only (one header, `BinaryStream.h`, six uses). `string::starts_with` appears
  once, in `BellTar.cpp`, which is not needed. A host g++ -std=gnu++17 pass over all 60 C++ files finds nothing else
  (two missing `#include`s and the Linux mDNS file's unqualified `make_unique`).
* mbedTLS: bell guards its one 3.x call (`mbedtls_pkcs5_pbkdf2_hmac_ext`) with `MBEDTLS_VERSION_NUMBER < 0x03030000`, so
  2.28 works. bell's TLSSocket needs `mbedtls_net_*`, which the PS3 config does not build; the sx_tls layer replaces it.
* The real gaps are in the PS3's libstdc++, built without threads: no `<mutex>`, `<condition_variable>`, `std::lock_guard`
  and friends (about 70 uses), no `std::to_string` / `std::stoi` (7), and no `std::snprintf` / `std::strtoull` / `std::strtof`
  in namespace std (nlohmann json, `Utils.h`). A 40-line stand-in header set removes every error in cspot's own 17 sources;
  what is left is `netinet/tcp.h` (PSL1GHT has no such header) and the MP3 codec. The real replacements (mutex, condition
  variable and semaphore over lv2 with `sysMutexAttrInitialize`, sockets, the TLS socket over sx_tls, an mDNS responder,
  a small HTTP server for the `addUser` endpoint instead of civetweb, a PCM sink) are the SP3 work, about 1,500 lines.
* The `pregen/protobuf` nanopb output of Switify's tree avoids needing `protoc` in the build.

### 4. SP2: big-endian proof of the parts that do not need the network (done)

`tests/spotify_be/run.sh` builds the cspot core for x86 and for powerpc64 (static, `qemu-ppc64`) and compares: the
Shannon cipher and MAC over odd-sized chunks (and its decrypt round trip), `Utils` (`hton64`, `pack`, `extract`,
`bigNumAdd`, hex), nanopb encode and decode of a keyexchange `ClientHello` and a mercury `Header`, and Tremor (bell's
integer Vorbis decoder) over a 2 s stereo Ogg: every line is identical on both machines apart from `hton64`, which is
the byte swap on x86 and the identity on the PS3, as intended. The audit found no bug. Not covered because it needs a
logged-in session: the AP handshake, AES-CTR decryption of real audio, and the CDN reader.

### 5. What a decision unblocks

* If the user accepts the web-player client id as part of cspot's standard flow (as for SoundCloud's), SP3 and SP4 are
  buildable; pairing then happens on the PS3 itself (SP3 includes the mDNS responder), and the first log line of SP0 is
  whether audio keys are granted. Prior art says some newer accounts are denied; that is the gate.
* If not, the Spotify tab cannot work through cspot, and Spotify stops here (the server-plugin fallback uses go-librespot,
  which has the same client id, so it does not get round this either).

## Memory: why nothing is held whole (this supersedes the buffering described under SC1/SC2 above)

The first run of the console check in the emulator (RPCS3, `BUILD_FOR_RPCS3=1`, the real PPU code with the app's own
reservations) found that **the process has about 120 KB of main memory left after boot** (`sys_memory_get_user_memory_size`
via `meminfo`; the log line `7f reserve done: free=3512KB` is the figure just after the video reservations, and the
disk, USB and download threads take most of the rest). A 128 KB thread stack is fine; a 256 KB one failed with ENOMEM, and
reading a 200 KB segment into a buffer failed in `realloc`. The host tests had never shown it. So:

* `sc_jstream`: the listings (50 tracks = 150-250 KB of JSON) and playlist documents are parsed one element at a time
  (work buffer 32 KB, any element larger is skipped and counted).
* `sc_hls`: durations (4 bytes a segment) plus one URI template; SoundCloud's 360-segment mix costs 1.5 KB instead of 300 KB.
  A playlist that breaks the "counter in the file name" pattern keeps every URI (up to 96 KB), else is refused.
* `fmp4_parse_head` + `sc_dec`: a segment is read as a stream through a 20 KB window: the head (styp/sidx/moof) is parsed,
  then each frame is read and decoded in turn; `sc_source` resumes a dropped connection with a Range request.
* `sc_html`: the 70 KB home page streams through a script finder.
* A track record is 330 bytes (artwork kept as its thumbnail key, transcoding URL without its constant start); a listing
  keeps a window of 150 tracks and forgets the oldest 50 when paging on.
* Idle TLS connections (about 40 KB each) are flushed after the API calls so only the media connection stays open.
* The new threads use 128 KB stacks (the artwork provider runs its TLS on a worker because the thumbnail thread has 64 KB).

Tests: `test_jstream` (every fixture at every chunk size, truncations, malformed input), `test_sc` (templates, irregular
playlists, limits, the streaming parsers against the whole-document ones), `test_dec` (identical output at chunk sizes
1 to 100000, and a connection that dies mid-segment), `test_fmp4` (the incremental head parse). All also run big-endian.
