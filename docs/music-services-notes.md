# Music services (SoundCloud, Spotify) notes

Branch `feature/music-services`, worktree `~/jf-music`, base `fix/3.2.2` @ 5796bc9. Design and rules:
`HANDOFF-music-channels.md` in the workspace root. Nothing here is released, pushed or deployed.

## Rules the code is held to

1. Stream only: no audio on disk, no offline mode, no cache of encrypted files.
2. No DRM circumvention. SoundCloud tracks whose only transcodings are `cbc-encrypted-hls` or
   `ctr-encrypted-hls` are hidden; their key URIs are never fetched. Snipped previews are skipped.
3. No other vendor's client credentials are used or extracted.
4. The client id, tokens and credential blobs are never logged or committed.

## SC0: network layer

* `source/net/sx_*` is a separate module; the Jellyfin path (`http.cpp`, firmware SSL) is untouched.
* `sx_tls_init()` runs in `main.cpp` right after `http_init()` / `net_selftest_run()` and before the VDEC
  reserve, because it allocates (RNG, parsed CA bundle) and the reservations leave little heap.
* Host: `make -f tests/Makefile.music check` (TLS/HTTP against a local server, ChaCha/AES, expired cert).
* Console check (the user's step): create `/dev_hdd0/tmp/jellyfin_sc_test.txt` (any content), start the app,
  then read `/dev_hdd0/tmp/jellyfin_sc_test_result.txt`. It walks the whole chain (client id, resolve, stream
  URL, playlist, init segment, segment 0) on a worker thread and deletes the gate file when it starts.

### Measured 2026-10-16 on this PC (host mbedTLS, same code)

* client id scrape 343-378 ms, resolve ~150-200 ms, stream URL ~60-95 ms, playlist ~220 ms, segment 0 ~80 ms.
* Bundled roots verify `soundcloud.com`, `api-v2.soundcloud.com`, the script host `a-v2.sndcdn.com` and the
  media CDN `playback.media-streaming.soundcloud.cloud` (Amazon chain).
* Signed media URLs are ~840 characters, so every URL buffer is `SC_URL_MAX` (1536).

## SC1: pure client (`source/svc/sc_*.c`)

* `sc_scan`: byte state machine for `client_id:"<32 alnum>"`. The same script holds `google_client_id:"..."`
  and `apple_id_client_id:"..."`; a hit needs a non-`[A-Za-z0-9_]` byte before it, exactly 32 alphanumerics and
  a closing quote. Tested with every split point and byte-at-a-time.
* `sc_hls`: media playlists. Any `EXT-X-KEY` / `EXT-X-SESSION-KEY` whose METHOD is not NONE is refused before a
  URI is looked at. Master playlists and byte ranges are refused. Durations are rounded to the millisecond.
* `sc_api`: URL builders, parsers and the transcoding rule (see header). `sc_url_with_cid` only ever adds the
  client id to `https://api-v2.soundcloud.com/`.
* `sc_net`: client id scrape, API calls with 401/403 refresh-and-retry, stream URL resolution. API URLs carry a
  placeholder; the real id is substituted for the one request on the stack.
* Fixtures: `tests/fixtures/sc/` (recorded 2026-10-16, secrets replaced). The real audio segments are
  all-rights-reserved and live only in the gitignored `tests/fixtures/sc-private/`.
* Test: `tests/svc/test_sc.c` (516 checks) x86 with ASan/UBSan and big-endian under `qemu-ppc64`.

## SC2: playback chain (source/svc/fmp4, sc_aac, sc_dec, sc_source)

`sc_source` (playlist + on-demand segment fetch, retry, signed-URL refresh) -> `fmp4` (init/segment reader) ->
`sc_aac` (libfaad, raw frames from the init segment's AudioSpecificConfig) -> `resample.c` -> 48 kHz stereo floats.
`sc_dec` has the shape of local_audio's `la_open` / `la_decode` / `la_seek`, so the music engine drives a SoundCloud
track the way it drives a file.

* The Yo! Player port's `demux-mp4.c` reads through a random-access video source, so `fmp4.c` is a rewrite for
  whole in-memory segments that follows its fragment handling (tfhd/trex defaults, tfdt, trun flags). No Yo! code is
  copied, so no Apache NOTICE is carried; the idea is credited in the header.
* Demux checked frame for frame against ffmpeg's demuxer on ffmpeg-made DASH segments (`fixtures/sc_synth/make.sh`,
  own tones, generated at test time): 1078 stereo and 564 mono frames identical, including truncation and byte-flip
  fuzzing. SoundCloud's real init segment parses (44.1 kHz, stereo, AAC-LC, 2-byte ASC).
* Decode checked against ffmpeg's decoder: max difference 1.4e-4 (mono 48 kHz) and 2.2e-4 (stereo 44.1 kHz through the
  resampler). **Big-endian: the same test under `qemu-ppc64` with libfaad 2.7 (the portlibs' version, built by
  `~/st-tools/faad-be/build.sh`) passes with max 1.44e-4 / 1.90e-4.** It takes about 3 minutes under qemu.
* Seeks: the segment's tfdt places the target exactly (the playlist's rounded EXTINF only picks the segment), two
  frames of lead-in are decoded and dropped. libfaad's PNS noise runs on across a stream, so a seek re-rolls noise in
  bands that use it: sample differences stay under 5e-4 against a 0.0625 tone.
* `scaac_reset` reopens the libfaad handle instead of `NeAACDecPostSeekReset`, so a seek to 0 is bit-identical to a start.

### Measured on this PC against the real service (`live_play`)

* Free track (Forss, "Flickermood"): playlist in 325 ms, first sound 423 ms after the playlist request, seeks produce
  audio in 38-118 ms, the last segment ends cleanly after 8.9 s, and a forced re-resolve (an expired URL) is
  transparent (`refreshes=1`).
* 23 real liked tracks from two profiles (160 and 96 kbit/s AAC, all 44.1 kHz): all decode, 0 bad frames.
* Not measured: console CPU and heap, TLS speed on the PS3, how long a segment takes there. That is the user's SC0/SC-TV step.
